# MoodSwings Unity client

A native mobile/desktop client for the same MoodSwings backend
`php-app/` and `web-static/` already serve to the browser. This
directory is scaffolding, not a working project yet -- it was created
outside the Unity Editor (this session has no GUI/display and can't run
the Editor), so it's deliberately minimal about anything Unity itself
needs to generate.

## What's here vs. what Unity generates

Committed:

- `Assets/` -- empty script/scene/prefab folders to start from
  (`Scripts/Core`, `Scripts/Networking`, `Scripts/UI`, `Scenes`,
  `Prefabs`, `Editor`), plus one real script:
  `Assets/Scripts/Networking/ApiClient.cs`, a starting point for talking
  to the existing JSON API (see "Talking to the backend" below).
- `Packages/manifest.json` -- a reasonable baseline package/module list
  for a blank project. Unity's Package Manager will resolve/update exact
  versions and add any additional built-in modules it needs the first
  time it opens this project -- don't worry about this file being
  slightly stale.
- `ProjectSettings/ProjectVersion.txt` -- pins an Editor version so
  Unity Hub knows what to open this with. Currently pinned to
  **Unity 6000.6.3f1** (Unity 6.6); install that Editor via Unity Hub
  to open the project.
- `.gitignore` -- Unity's own standard template
  (`Library/`, `Temp/`, `Obj/`, `Build/`, `Logs/`, `UserSettings/`, ...),
  scoped to this directory.

**Editor-generated files:** the rest of `ProjectSettings/` (`ProjectSettings.asset`, `TagManager.asset`, `EditorBuildSettings.asset`, etc.), the `.meta` files, and `Packages/packages-lock.json` were generated by opening the project in Unity 6000.2.1f1 and are committed as the Editor-verified project state. Let the Editor maintain them; don't hand-edit.

## First-time setup

1. Install Unity Hub and Editor version 6000.6.3f1 (matching
   `ProjectSettings/ProjectVersion.txt` above).
2. In Unity Hub, **Open** (not "New Project") and point it at this
   `unity-client/` folder directly. Unity will recognize the existing
   `Assets/`/`Packages/manifest.json`/`ProjectSettings/ProjectVersion.txt`
   and fill in every other `ProjectSettings/*.asset` file with its own
   defaults on first load.
3. Once it opens cleanly, `git add`/commit the newly-generated
   `ProjectSettings/` files (everything except what `.gitignore` already
   excludes) -- that's now the real, Editor-verified project state.
4. From there, treat this like an ordinary git-tracked Unity project:
   commit `Assets/`, `Packages/`, and `ProjectSettings/`; never commit
   `Library/` or the other Editor-generated caches.

## Talking to the backend

`Assets/Scripts/Networking/ApiClient.cs` wraps the same JSON HTTP API
`web-static/js/app.js` already calls (see `php-app/public/index.php`
for the full route list and `php-app/README.md` for what each one
expects/returns). Things worth understanding up front:

- The API is mounted under **`/app`** on the site root
  (`ApiConfig.ApiBase`); static files (card art, `VERSION`) are at the
  site root.
- Auth is a server-issued **cookie** (`session_token`), not a bearer
  token -- `UnityWebRequest` doesn't persist cookies the way a browser
  does, so `ApiClient` captures `Set-Cookie` itself and replays it as a
  `Cookie` header. Where the token is kept between launches is an
  `ISessionStore` -- see "Login and sessions" below.
- Every request sends an explicit `User-Agent` (`MoodSwings/<version>
  (<platform>)`): the host's filter answers 406 to some generic agents
  (Python's default, a bare `Mozilla/5.0`).
- Calls return `ApiResult<T>`: `Ok`, or a `Failure` kind (`Network`,
  `Unauthorized`, `Maintenance`, `Rejected`, `Server`, `InvalidResponse`)
  plus the server's message. `MaintenanceEntered` / `SessionExpired`
  events cover the two cases every screen needs to react to.
- JSON is Newtonsoft (`[JsonProperty("snake_case")]` models, not
  `JsonUtility`).
- HTTP goes through `IHttpTransport`, so `ApiClient` is tested against
  `FakeHttpTransport` (`Assets/Tests/EditMode`) -- run them from
  Window > General > Test Runner > EditMode.

Add routes as extension methods next to `AuthEndpoints` rather than
growing `ApiClient` itself.

## Rendering

The project uses the **Universal Render Pipeline (URP)**: Unity deprecated the
Built-In Render Pipeline in 6.5 and Unity Hub flags projects still on it. The
assets live in `Assets/Settings/` (`URP.asset`, `URP-Renderer.asset`) and are
the default pipeline for every quality level. Settings suit a uGUI-only,
unlit app on mobile: no HDR buffer, no MSAA, no shadows. Color space stays
Gamma so UI colors are unchanged. **MoodSwings > Set Up URP** (or `-executeMethod
MoodSwings.Editor.UrpSetup.Apply`) recreates/reapplies all of it. Anything
that needs lighting or post-processing later should revisit these.

## Feedback: sound, vibration, animation

`BoardCues` (UI-free) works out what happened between two looks at a game -- a
mood entered play, the turn came to you, a question for you, a round or the game
ended, someone else spoke -- and the board reacts to each:

- **Animation:** a played card slides from its player's seat (or your hand) to its
  place on the table; round and game results are announced for a few seconds.
- **Sound:** short placeholder tones and a thump, synthesized in code
  (`SoundBank`) because the repo has no sound files. Replace `SoundBank.Create` with
  real clips when there are some; nothing else needs to change.
- **Music:** `MusicPlayer` plays the main theme while the app is open. On the board it
  crossfades (two seconds) to the theme of the color of the mood played most recently by
  anyone (read from the game's recent events -- the in-play list is ordered by card, not by
  when it was played; the main theme again once the round has been scored, until something is
  played in the next), and leaving the board brings the main theme back. Each theme keeps its place while it is
  faded out. The tracks are `Assets/Resources/Music/{main,white,blue,black,red,green}.mp3`
  (`MusicImporter` streams them as Vorbis rather than decoding them into memory); they came
  from `Boots_on_the_Tavern_Floor` (main), `Beneath_the_Willow_Canopy` (white),
  `Beneath_the_Iron_Bough` (blue), `Before_the_Fire_Dies` (black),
  `Beneath_the_Gallows_Tree` (red) and `Copper_Coins_in_the_Hat` (green). Replace a file to
  change a track.
- **Vibration** (Android): a short buzz for your turn, questions for you and your own
  plays, a long one for the end of a game. Needs a physical device to feel.
- The first draw of a game is not an event, so nothing plays when you open one. The
  switches (**Sound effects** with its **Effects volume**, **Music** with its **Music volume**,
  and **Vibration** on a phone) are under Settings > On this device and are stored on the
  device, not the account. The volumes are sliders that apply as they move.
- **Colors:** the palette is the game's own five colors -- white for the page, blue
  for what you act on, black for text, red for Resign and anything that can't be undone,
  green for good news -- in a light version (the default) and a dark one. Dark mode is
  under Settings > On this device and is remembered on the device; because screens take
  their colors when they are built, switching it rebuilds them and returns you to the
  main menu. All of the colors live in `UiTheme` (`Apply(dark)`); screens use its
  tokens (`accent`, `onAccent`, `raised`, `success`, `gold`, `faint`...) rather than
  literals.
- **Background:** every screen sits on a wood table, light or dark to match the palette
  (`Backdrop`, under all the screens, covering the whole display including a phone's notch and
  rounded corners; cropped rather than stretched to fit any shape, with a thin wash of the page
  color over it for legibility). The pictures are `Assets/Resources/Backgrounds/{light,dark}-background.jpg`,
  made by `tools/make_backgrounds.py` from the full-size originals. A screen's own backing is clear.
- **Phone screens:** each screen is fitted to the system's safe area (notches, rounded
  corners) and refitted on rotation (phones do not count their rounded corners as unsafe, so the dev server tag and the draft deck buttons sit further in from the corner); layouts were checked at 16:9, 20:9, 16:10 and 4:3.
- "Pause before your turn" (Advance turn) and "auto-pass on an empty hand" are the
  account preferences from Settings; the board honors them as the server applies them.

## Input

The project uses the **Input System** package (the old Input Manager is deprecated;
Player Settings > Active Input Handling is "Input System Package (New)"). Screens
read the few keys they need through `KeyInput` (Escape, Enter, Tab, Shift), and the
scene's `EventSystem` uses `InputSystemUIInputModule`, which also handles touch.
The Android Back button arrives as Escape. `InputSystemSceneTests` drive a virtual
mouse and keyboard to prove clicks, Escape and Tab really work; the other scene tests
call button handlers directly. Typing into a text box can't be simulated that way,
so it's worth a manual check after changing input settings.

## Login and sessions

`Assets/Scenes/Main.unity` is the entry scene (generated by
`MainSceneBuilder`; rerun **MoodSwings > Build Main Scene** after adding a
screen). Flow: `SplashScreen` (checks a remembered session via `/me`) ->
`HomeScreen` or `LoginScreen`; `MaintenanceScreen` takes over whenever the
server reports maintenance. Screens build their own UI in code
(`UiFactory`), and all decisions live in `AuthFlow`, which is tested
without any UI.

"Remember me" keeps the session cookie across launches via
`SecureSessionStore`, which encrypts it with the platform's own facility
before it touches `PlayerPrefs`:

- **Windows:** DPAPI (current-user key), via P/Invoke.
- **Android:** Keystore AES-GCM, in `Assets/Plugins/Android/SecureStore.java`.
  Verified on an Android 16 (API 36) x86_64 emulator under Unity 6000.2.1f1 --
  see "Android" below. Not yet re-run since the move to 6.6 (which can't
  target that emulator), and never run on a physical device.
- **macOS:** a random key in the login Keychain (through the system's `security` tool) encrypts it.
- **iOS:** the same encryption, with the key in the app's own Keychain
  (`Assets/Plugins/iOS/MoodKeychain.mm`, `IosKeychainKeyStore`). Written for the iOS build, which
  has not been run yet (see "iOS" below).
- **Anything else** (Linux): no secure storage yet, so sessions aren't remembered there.

It fails closed: a corrupt blob, a failed decrypt, or an unsupported
platform all mean "no saved session" -- never a plaintext fallback.
Unticking "Remember me" keeps the session in memory only.

## Main menu, friends and settings

`HomeScreen` is the main menu: Play (a placeholder until the lobby), Friends
(with a count of waiting requests), Settings, Log out. Escape (or Android's
Back button) goes back a screen.

- **Friends** (`FriendsScreen`, state in `FriendsFlow`): add by username or
  email, accept/decline incoming requests, see sent requests, and see which
  friends are online (a friend who hides their status shows no marker).
  Removing takes two clicks. The list refreshes every 15 seconds while it's
  open, since the server has no push channel. State is cleared on logout or an
  expired session.
- **Settings** (`SettingsScreen`, `PreferencesFlow`, `PreferenceCatalog`): the
  web Settings dialog's account preferences, minus the browser-only ones (card
  size, push notifications). Each toggle saves immediately and rolls back with
  the server's message if the save fails. `/login` doesn't return the
  preference flags, so opening Settings re-reads `/me`. To add a preference,
  add one entry to `PreferenceCatalog` -- the screen builds from it, and a
  test pins every route and JSON key to what `php-app` defines.

## Play, new games and the open lobby

**Play** (`PlayScreen`) lists your games -- ones waiting on you first (your turn,
or a card effect needing your choice), then the rest, then the most recent
finished ones -- with **New game**, **Open games**, and a **Rematch** button on
finished games it can recreate. The main menu's Play button shows how many
games are waiting on you. A game's board is Phase 4, so rows don't open yet.

- **New game** (`NewGameScreen`, `GameSetup`): either *invite friends and
  bots* (they're seated and the game starts at once; up to 3 opponents, since a
  game seats 4) or *post to the open lobby* for 2-4 total players. Pick a deck
  (Structure, Power, jceddy's 75, One of Each) and optionally let a bot go first.
  Traditional format only for now; the other formats, drafts and custom
  decklists arrive in Phases 7-8.
- **Open games** (`OpenGamesScreen`): join a posted game, take down one you
  posted, or leave one you joined. A game starts when its last player joins
  (the join response's `status` is then `started` instead of `ok`). Posting
  needs "Discoverable for open games" in Settings; the server says so if not.
- The state lives in `LobbyFlow`; `GameDisplay` turns games into the text shown
  (status lines, settings, opponents), with fallbacks for formats and decks this
  client doesn't know yet. Finished games include **abandoned** ones, which have
  no completion time and sort last.
- New menu screens extend `ListScreen` (header, status line, scrolling list,
  polling) -- Friends and Settings predate it and build the same by hand. Lists
  have an auto-hiding scrollbar.

## The game board

Open any game from **Play** (the **Open** button on a row), or watch someone
else's from **Watch**. `BoardScreen` draws it: every seat with its moods in
front of it and a scoreboard to its left, the tops of the cards in each hand along
its player's edge of the screen, the deck and discard peeking up either side of your
hand, and the turn banner, messages and **Pass** in the middle. Click any card for a
readable close-up (the table cards are too small to read). Playing is described
under "Playing a game" below.

- **Your hand** shows only the top of each card along the bottom edge -- the name and
  the value -- which leaves the room above it for the table. Hover a card for a large
  preview; tap it to play it, or drag it up onto the table.
- **Opponents' hands** are the backs of their cards peeking in from their edge of the
  screen (the top; the sides in a four-player game), one for each card they hold, so
  there are no hand counts in text.
- **A player's scoreboard** sits at the end of their hand that is at *their* left (so, for
  the player across from you, at your right): the points in a box with a trophy for each
  round won stacked beside it (dim ones for the rounds still to win), a **1ST** tag on the
  box for whoever went first this round, then their name, and the Hurt Feelings card for
  whoever has it. It is lit when it is their turn. In a duel, where each player has their own
  deck, its size shows too. A player who has unlocked an achievement has a **trophy beside
  their name** in the colour of their best tier (Bronze, Silver, Gold, Platinum or Diamond,
  the colours the web board uses; `highest_achievement_tier`); tapping it says which. On the
  turn holder's scoreboard, "2 plays left" is underlined: tap it for a list of where those
  plays come from ("Your normal turn", "An extra play from Charity" -- the server's
  `round.play_grants`, as in the web board's expandable plays panel). Like the note itself,
  the list is not there before the turn is acknowledged or once the game is over.
- **The deck and discard** peek up from the bottom edge, the discard at the far left and the deck at the far right of the bottom edge, with your scoreboard
  and your hand between them, with a line above each: "Deck 30", "Discard 3" (and
  "play from it" when an effect makes a card in it playable). Tap the deck for its
  list, the discard to look through it.
- **Ongoing effects** are shown on the table. A mood whose "While in play" ability is
  doing something right now -- its value has moved because of it, the server lists it
  among the effects changing scoring or the board, or it is acting on another mood --
  has a halo in its color that breathes and a ring that spreads outwards from it and
  fades. One that is switched off (suppressed, shown on its side) or only waiting for its
  condition doesn't. When one mood is acting on another, a curve runs from the source
  to the target with glowing dots streaming along it: red for a suppression, blue for a
  dice-value boost, amber for a mood held by someone else because of it
  (`BoardEffects` works out which, from `suppressions`, `boosted_by_card_id`,
  `temporary_ownership` and `affecting`; `CardAura` and `EffectLinksLayer` draw them).
  Neither takes a tap.
- **The middle of the table** is kept small, to leave room for cards: no "whose turn" line
  (the scoreboards light up for that) and no "First to 3 wins" (the trophies say it). What
  is left is the round, game and match line, the clock, messages, "2 plays left" when you
  have plays to spare, any question or result, and a modest **Pass** / **Next game** button.
- **The menu** (three bars, upper left; a badge on it counts unread chat) slides in a
  panel from the left: **< Lobby**, **Resign**, and a **Log** tab (the recent events
  and any effects in force) and a **Chat** tab (the game's messages, with a box to
  answer). It opens on the chat when there is something unread, and the tab shows only
  how many are unread ("Chat (2)"), not how many there have ever been. What has been read is remembered per chat, as the
  newest message id read: a draft match shares one chat between its games (`draft_match_id`), so the next game of the
  match carries on from what was read in the last instead of showing every old message as unread again
  (`ChatThreads`; a game outside a match has a chat of its own, and a count remembered by an older version is converted). The client's
  version is in its lower left corner.

- **Seating matches the web client exactly** (`BoardLayout`, from
  `inPlayZoneAssignments()` in `web-static/js/game.js`): you at the bottom, and
  the **next seat in turn order at your left**. That's not cosmetic -- the engine
  defines a player's "left-hand neighbor" (Confusion, Avoidance...) as the next
  seat, so a board that seated people differently would contradict the cards.
  2 players: opponent across; 3: top-left and top-right; 4: left, across, right.
- **It polls every 3 seconds**, and that's functional: the server advances bot
  turns and enforces timers as part of answering `GET /games/state`. It redraws
  only when the game actually changed, and if a refresh fails it keeps the last
  board up with a message instead of blanking.
- **Cards** (`CardView`) use the converted art when present and a drawn stand-in
  (name, value, rules text) when not, so the board never depends on the art. The
  art prints a card's main value in its top-right corner, so when an effect has
  **changed** a mood's value, a chip is laid over that corner showing the current
  one; an unchanged value gets no chip, and neither does a mood turned onto its printed alternate value (below), whose
  turned art already prints that number there (the web client's rule; not when a Chaos Draft adjustment has moved it).
  (Cards in hand always have their printed
  value, so only moods in play get one; a stand-in card, which prints no value,
  always shows it.) The chip is placed by fractions of the card, so it stays over
  the printed value at every card size. A **suppressed** mood lies on its side
  (only the face turns; the label and chip stay upright), is labelled SUPPRESSED,
  and its close-up says "Suppressed by <card>" -- suppression only makes the value 0.
  A mood that is on its **alternate value** (`BoardCard.IsAltValueActive`) is turned 180 degrees, by tabletop
  convention: the alternate value is printed upside down in the lower left corner of the art, so turning the card brings it to
  the top right, where the value is read. The server says when, with the two flags the web client turns a card for:
  `alt_value_active` (a "while in play" mood whose own condition holds right now -- "While in play, this mood's value is 6
  if ...", following the board and going false when it stops holding) and `value_locked` (an "After playing ... its value
  becomes 7" has locked it in). The server leaves `alt_value_active` false for a suppressed mood, a Chaos Draft value, and
  an alternate value that is only a dice number from Encouragement or Idealism, so those aren't turned. A suppressed mood
  with a locked-in value is three quarter turns; one only suppressed (value 0) is the quarter turn above. Only the art
  turns -- the badges, the value chip and the close-up stay upright, and the close-up says why the card lies the way it
  does. A drawn stand-in (no art on this machine) isn't turned, since its text would be upside down.
  A mood **recolored** by an effect (Imagination) wears a pill in its current color naming it (BLUE),
  and its close-up and hover preview say "Color is now blue (printed green) - changed
  by Imagination" (the effect is found from the board-wide effects the server lists).
- **Spectating** uses the same board with no hand and no seat of your own
  (anchored on the first seat, as the web does): a friend's in-progress game, or
  a spectate code a player shared.
- The Hurt Feelings token shows on the seat that holds it (3+ player games).

### Playing a game

- **On your turn**, click a card in your hand: its **play form** opens with the
  card large on the left and, on the right, whatever playing it asks you to
  choose (nothing, for about half the cards). Cards you can't play right now are
  dimmed in your hand and open a form whose **Play card** is off, with the reason.
  **Pass** sits in the middle of the screen and **Resign** (which asks first) is in the menu; **Advance turn**
  replaces Pass when "pause before your turn" is on and the turn is waiting for you.
- **A question for you** -- a card effect waiting on your answer (Confusion's
  "give a card", Fury's "discard a mood", Duplicity's repeat offer, ordering your
  after-scoring effects, Enthusiasm's and Passion's bonuses) -- opens a form by
  itself and can't be called off; the round is frozen for everyone until it's
  answered. If the server turns an answer down, the question is rebuilt fresh from
  the latest board. While someone else is deciding, the banner says who.
- **Choices come from the server.** Every card in your hand arrives with a list of
  typed fields (`choice_fields`, from `CardChoiceSchema.php`); a pending decision
  carries one the same way. `ChoiceForm` (UI-free) works out the legal options for
  each field from the board, tracks what's picked, applies the counts and
  constraints ("exactly 2", "one mood per player", "combined value 5 or less"), and
  builds the `choices` body -- all mirroring the web client's panel. The server
  checks everything again; these checks only catch a mistake before sending. Moods
  are listed under their owner; every control is a tappable button, so nothing needs
  a drop-down or a modifier key. A legal play that would do nothing (an optional
  target left blank, Wrath's box unchecked) asks "Play anyway?" first. Creativity's
  form takes on the questions of whichever mood it copies. Duplicity's repeat offer
  gets the same questions about the repeated mood's choices (with "Repeat anyway?"),
  but only when "Repeat again?" is ticked, and its choices start from the server's
  defaults like the original play's.
- **Starting.** A waiting game is started by the board once it can be: at once for
  an ordinary game, after everyone presses **I'm ready** in a synchronous one
  (whose header then shows the **action clock**, ticking every second).
- Every action is refused while another is in flight, and re-reads the board
  afterwards even when the server said no (a "not your turn" after a double tap
  means the board moved on without you). Round and game endings are announced.
- **Dragging.** On your turn a card can also be dragged from your hand onto the
  table (anywhere above the hand): a ghost follows the pointer and the table lights
  up as the place to drop. A card that asks for nothing is played at once; one with
  choices opens its form; one that can't be played says why; letting go over the hand
  puts it back. Mouse and touch both work.
- **Hover.** On desktop, resting the mouse on any card for a moment shows a larger
  copy on the opposite side of the screen (with its current value and what is
  suppressing it); touch has the click close-up instead.
- **Not playable yet:** tournaments and anything else with a format the app doesn't know (the
  board still shows them; the header says they can't be played in the app yet).

### Other ways to play

- **Duel** gives each player a deck of their own (so the deck pile reads "Your deck 25", and
  the others' counts are on their seats). **Synchronous** games are two players sitting down
  together: a ready check and a 30-second action clock (shown in the header). The server has a
  feature switch for it, which is off on the dev server, so the New Game option stays hidden
  until it's on.
- **Best of three** (two players in Traditional or Duel, or any team game): first to win two
  games, the next created for you. The header says "Game 2 - Match: you 1 - 0 BotSage"; game 2
  or 3 opens with a question for the previous game's loser (who can see their opening hand
  behind it) -- do they go first, or let the winner -- that can't be dismissed; a game that ends
  with the match still on offers **Next game**; a decided match is announced.
- **Team play** (Open: partners side by side, who see each other's hands; Closed: across the
  table, with private hands and two cards passed at the start). Teams score together, shown in
  the header. When it's your team's decision (who goes next, or who gets the shared draw), you
  name someone and your partner agrees or sends it back; otherwise the banner says who is
  deciding. Open Team Play has a **Partner's hand** button and chat that can go to just your
  partner. New Game needs exactly three opponents and a partner picked from them (or left to
  chance); a lobby team game seats four and draws teams once they've joined; the 15-card Power
  deck isn't offered. No team game has been captured, so team play is checked against the
  four-player capture turned into team games, with the fields as the server documents them.
- **Puzzles** (Home > Puzzles): standalone solitaire puzzles, easiest first, each with its
  goal and how you've done. Attempt (or Try again) starts a fresh game on the ordinary board,
  with the goal kept in view, a Hint button for the puzzles that have one (the server is told
  first, since reading it costs an achievement), no Resign (just leave), and "Puzzle solved in N
  plays!" at the end.

### Drafting

- **Quick Draft** (New Game > Draft): the board shows the draft where the table would be. Each
  stage is a pile of cards: tap two to keep (the eye on a card shows it large without
  choosing it), then **Keep these cards**; the rest are passed on, and the cards you've kept so
  far stay in view below. Your choice survives the board's refreshing every few seconds.
- **Winston Draft:** three piles that grow. On your turn the pile you're looking at is face up
  (the others are face down, with their sizes); **Take pile N**, or **Pass** to see the next --
  passing the third draws from the deck, and asks first when that would get you nothing. The
  other players' card counts and last move are listed.
- **Grid Draft:** the face-up grid, with **Row N (cards left)** / **Col N** buttons around it. Tap
  one to light that line up and read "Take row 2 (3 cards)" on the button; tap again (or another
  line) to change your mind. Lines with nothing left can't be chosen. Everyone's picks so far
  are shown, being open information, grouped by team in team games.
- **Rotisserie Draft** and **Tiered Rotisserie Draft:** the shared pool, sorted by colour and
  rarity. On your turn tap a card (the button then reads "Draft <name>") and confirm with it --
  one tap on a card never commits, unlike the web, so a slip on a phone is harmless. The tiered one
  shows its tiers above the pool ("Tiers: Common (done) > [Rare, 4 picks each] > ...").
- **Sealed Deck, Sealed Pool of the Day, Weekly Sealed Pool:** no drafting at all -- you start at
  deck building with the pool you were dealt. The Pool of the Day (two players, the same 50-card
  pool for everyone that day) caps Rares and Mythics, which the status line states and the line under
  the cards enforces ("At most 1 rare cards (3 chosen)"). Sealed Deck is also offered next to
  the team formats' decks; the Pool of the Day holds exactly one opponent. (A weekly pool match
  is made by the server's queue, so there's nothing to set up here.)
- **Chaos Draft** (switch on "Show custom card/effect formats" in Settings to be offered it): drafts
  as Quick Draft does. Once the game is under way, every round opens with a choice of two
  effects, read from the server on every refresh: pick one, then the card in your hand it goes on
  (in Open Team Play, your partner's too -- one of you proposes, the other agrees or sends it back),
  then **Attach**. Nobody can play or pass until everyone has attached theirs, and the banner says
  who is being waited for. A card carrying an effect has a **CHAOS** pill (coloured by the
  effect's rarity) and its detail and hover text give the effect and any change to its value. When a
  repeating effect sets up a loop, a box offers to apply it up to a cap of times at once. Like any question, the
  offer can be set aside with **View board** to look at the table (the effect already chosen stays chosen), and
  **Back to decision** brings it back.
- **Building the deck** follows the last round: every card in your pool starts in your deck, tap
  one to take it out (or put it back), **Clear** / **Select all**, and **Submit deck** once it is
  within the size limits (and any rarity caps) -- the line under the cards says what's wrong. A
  later game of the match starts from the deck you last played. When every deck is in, the board
  starts the game and the table replaces the draft.
- A draft is always a best-of-three match, so the Best of three option isn't offered, and a
  lobby draft lets you choose 2 to 4 players. New Game's **Draft** format offers the five types;
  **Cards to draft** is the pool they deal from (Random 48, Structure, jceddy's 75 or One of Each;
  saved decks and pasted lists come with the deck builder), and Rotisserie also asks how many
  cards each player picks (13 to 20). Tiered Rotisserie uses the fixed rarity tiers. Open and
  Closed Team Play offer the same draft types next to their ready-made decks. What you've
  selected is kept when the board refreshes, and the list doesn't jump back to the top. No draft
  has been captured from the dev server, so this is checked against states built from the
  server's documented shape.

### Decklists and the deck builder

- **Home > Decklists** lists your saved decks (open one to change it, or delete it after being
  asked) and the decks friends have shared (a friend's can't be changed, so it opens as a copy).
- The **deck builder** shows every card on the left -- filter by color and rarity, or search names
  and rules text -- with the deck on the right: a name, **Share with friends**, and a line per card
  with its copies and a minus/plus. Tap a card to add a copy; its eye shows it large. **Save
  deck** makes a new deck or updates the one opened; leaving with unsaved changes asks first. A deck
  of fewer than 15 cards gets a reminder, since a game's custom deck needs at least that many.

### Playing a saved deck

- **Custom Deck** (Traditional and the team formats): the whole table plays one saved deck, which
  New Game asks you to pick from your decks and your friends' shared ones; it needs at least 15
  cards, and 15 more for each player beyond two (the Start button stays grey until it is big
  enough).
- **A saved deck as a draft's pool:** in a draft, **Cards to draft > A saved deck** deals the
  picks from one of your decks, copies and all.
- **Custom Decklists (Duel):** pick the deck-building rules (Structure, Power Duel or jceddy's 75),
  and a saved deck for each practice bot you seat. Once the game is made, each player chooses a
  saved deck on the board's waiting-room screen, which states the rules; when every deck is in the
  game starts. A Power Duel played as a match can allow **sideboarding**: for games 2 and 3 the
  screen shows your last deck and its sideboard together, starting from the deck you played, and
  checks the size, rarity and copy limits as you tap cards in and out. (Rules of your own making,
  and pasting a deck from text, are web-only for now.)

## Art packs (your own card art)

**Settings > Card art** lists **Default** (the art that comes with the app) and every art pack that has been added;
tap one to use it. A pack that doesn't have a card leaves that card on the default art, so a pack can replace a few
cards or all of them. The choice is stored on the device.

- **A pack** is a folder, or a `.zip` with the same layout, of **PNG or JPG** images. Card faces go in a folder named
  for their **set code**, in capitals -- `MSW/12-faith.png` (`MSW` is Mood Swings, the only set so far) -- with the
  card's number first (the catalog number, the same one the `art-overrides` and the web client's art files use; it
  is unique across sets, so a card is found in whichever set folder has it, the base game's first). Also
  `012.jpg`, `12.png` or `Card 7 - courage.png`. Images **outside any set folder are read as MSW**, so a small
  pack can be flat. The card back (`back.png`) and Hurt Feelings (`hurt-feelings.png`) sit **at the top of the
  pack**, not in a set folder. WebP isn't supported (Unity can't read it at run time). Images are shrunk to at
  most 1040 px tall; the card art that ships is 744 x 1040, so that shape looks right.
- **Examples:** three packs, **Original Mood Swings Art** (all 138 cards of the original art), **AI Assisted Mood
  Swings Art** (the AI-assisted art the app has shipped with: all 138 cards, the Hurt Feelings card and the card back) and
  **Hand Made Mood Swings Art** (the hand-made art that is replacing it a card at a time, so only the cards finished so
  far), are attached to the GitHub release `example-art-pack-msw` as `Original-Mood-Swings-Art.zip` (82 MB),
  `AI-Assisted-Mood-Swings-Art.zip` (166 MB) and `Hand-Made-Mood-Swings-Art.zip`.
  `python tools/make_art_packs.py --original <folder> --ai-source <folder> [--handmade <folder>]`
  rebuilds them: the original art's folder (already laid out as a pack) is zipped as it is, and the folders of finished
  card faces (`<number>-<name>.png`, plus `card-back.png` and `hurt-feelings.png` where there are any) are laid out as the
  other two. Each comes out as a folder and a `.zip` (next to the original art's folder, or at `--out`). Unzip
  one to see the layout, or add it as it is.
- **Replacing the art the app ships with:** `python tools/import_card_art.py <folder of finished cards>` turns the
  PNGs into `art-overrides/<number>-<slug>.webp` (replacing that card's earlier image), the Hurt Feelings card into
  `art-overrides/hurt-feelings.webp` and the card back into `Assets/Resources/UI/card-back.png`, then regenerates the
  Unity copy; commit `art-overrides/` afterwards. The hand-made cards go in this way, one by one, and keep the artist
  credit printed on them.
- **Adding one:** **Add a folder...** / **Add a .zip...** open the system's own dialog (PowerShell's on Windows,
  AppleScript's on macOS, the document picker on Android -- which needs no storage permission). The images are
  **copied into the app's own storage** (`<persistentDataPath>/ArtPacks/<name>/<SET>/<number>.png`), so the pack keeps working if the
  original moves, and on Android, where a chosen folder can't be read in place, the picker first copies it to the cache.
  Files that aren't card art are skipped and the status line says how many (and why, for the first).
  **Remove** (two taps) deletes the app's copy only.
- **Limits:** 12 MB a file, 600 files and 400 MB a pack; a zip entry's own file name is all that is used (never its
  path).
- **Code:** `ArtPackStore` (adding, listing, removing; UI-free), `CardArtLibrary` (the active pack's image first,
  then the shipped art; pack images are loaded and GPU-compressed the first time a card is drawn),
  `FilePickers` and `Assets/Plugins/Android/ArtPicker.java` (the dialogs). The Android picker has been compiled but
  **not yet run on a device**.

## Chat and emoji

The board's menu has the table's chat. Under the box are the quick buttons the web client has -- **GL;HF**, **GG** and five
emoji -- which send at once (what is in the box is left alone); the smiley beside the box opens a picker of about a hundred
emoji, which puts `:shortcodes:` (like `:skull:`) in the box, and a shortcode is turned into the emoji itself when the message
is sent, so the web client and the other players see the real thing.

The app's text system can't draw emoji: its font has none, and Unity's legacy `Text` skips every character outside the Basic
Multilingual Plane, whatever the font. So `EmojiText` (UI) replaces each emoji it has an image for with a blank of the right
width and lays the image over the blank once the text has been laid out; an emoji it has no image for is left out rather than
shown as an empty box. `EmojiSet` (Core) finds emoji in text and expands shortcodes. The list and the art live in
`Assets/Resources/Emoji/` (`emoji.txt` and one 72 px PNG each), made by `tools/fetch_emoji.py` -- edit the list there to add
more and run it again.

Emoji art: [Twemoji](https://github.com/jdecked/twemoji), graphics licensed CC-BY 4.0 (credited in the picker too).

## Weekly Sealed Pool and notification settings

## League

An open-ended event run from the server: you keep a permanent card collection and play best-of-three Duels against
other members, using only cards you own.

- **Play > League** shows the running event (or says there is none), your record, how many of your two allowed matches
  are going, the rules, and your matches (**Open game** for one under way, **View** for a finished one). **Join League**
  joins the event -- the first time grants a random Structure deck for your collection -- and queues you for a match;
  there is no deck to choose here. A game appears at once if someone was already waiting, otherwise **Leave queue** takes
  you out and the screen checks for a match every few seconds. **View my collection** is every card you own, with how many
  copies (tap one to read it).
- The **Leaderboard** is the running event's standings or, with **Previous event**, the last one's: rank, record and "top
  N%", you marked, ties sharing a rank. (The ranking score itself is never shown.)
- **Building the deck happens in the game.** Before each game of a match the board shows your pool as thumbnails with how
  many you own (lower right), how many are in the deck (lower left) and in the sideboard ("SB 1"). Tap a card for a
  popup with **-** and **+** for the deck and, on game 1, the sideboard (up to three cards declared then; the League's
  mythic and rare caps and the copies you own are kept to as you go). **Reset** goes back to the suggested deck (your
  last game's; on game 1, the deck and sideboard from your last match, or the starter deck for a first match) and **Clear** empties it. From game 2 the pool is fixed at what game 1 declared and
  whatever the deck leaves over is the sideboard, so you can only swap between the two. **Submit deck** sends it as
  decklist text; the server checks it again.
- A League game has no **Rematch** (your opponents come from the queue and are never played twice in an event).

## Production and dev servers

The app talks to **production** (`https://moodswings.jceddy.com`) by default; a Development build and the Editor
start on **dev** (`https://moodswings-dev.jceddy.com`) instead. A hidden switch changes it while running: on the
login screen, **tap the version text at the bottom seven times in a row** (each within two seconds of the last).
The app signs out of the server it was on (taking this device's push token back first), forgets what it had
fetched, points at the other server, and stays on the login screen. While on dev, a red **DEV SERVER** tag shows in
the top-right corner of every screen. The choice is remembered on the device. Sessions are per server and never
carried across. Both servers share one Firebase project and one package id, so push works on either.

## Push notifications

The server side is built (`php-app`: `POST /notifications/device-token`, `FcmNotificationChannel`; see
"Native push (FCM)" in `php-app/README.md`), and so is the app's side of the contract: `PushFlow`
registers the device's token for whoever signs in, takes it back on sign-out, follows a refreshed token,
honours a per-device switch in Settings (shown only where push works), and opens the game, the friends
list or the achievements when the notification that launched the app points at one (`PushRoute`).

On Android the token comes from Firebase Cloud Messaging: `AndroidPushTokenProvider` asks for the
notification permission (Android 13+), then `Assets/Plugins/Android/MoodPush.java` fetches the token. The
Firebase project's settings are read from `Assets/Resources/Firebase/google-services.json` (project
`mood-bee14`, package `com.jceddy.moodswings`; they identify the project and aren't secrets, but restrict the API
key to the package and signing certificate in the Google Cloud console). Firebase is started from those values
rather than with the google-services Gradle plugin, so the Gradle setup is only the messaging dependency in
`Assets/Plugins/Android/mainTemplate.gradle`, `android.useAndroidX` in `gradleTemplate.properties`, and
`MoodPush.androidlib` (the `POST_NOTIFICATIONS` permission, with its own `build.gradle` because the generated
one has no namespace). Everywhere else push is simply not offered.

A notification tapped while the app is in the background opens it with the notification's link as an intent
extra; the app reads it on launch and when it regains focus (`PushRouter`).

**Server steps still needed** (no app change): in the Firebase console, Project settings > Service accounts >
**Generate new private key**; put that JSON on the server outside the web root, set `FCM_SERVICE_ACCOUNT_FILE` to
its path in `php-app`'s `.env`, and apply migration `0451`. Without it the app registers its token but the server
has nothing to send with.

**Verified:** the build includes Firebase Messaging, the bridge, the permission and the package id, and the flow
around the token is tested. **Not yet verified on a device:** the token request, the permission prompt and a
real notification arriving and opening the right screen -- that needs a phone and the server key above.

## Android

Install the Android Build Support module for the project's editor in Unity
Hub. It bundles its own JDK/NDK/SDK.

- **Build an APK:** **MoodSwings > Build Android APK**, or headless:
  `Unity.exe -batchmode -quit -buildTarget Android -executeMethod
  MoodSwings.Editor.AndroidBuild.Build` -> `Build/Android/MOOD.apk`.
  It forces IL2CPP and ARM64 only -- Unity 6.6 dropped x86/x86_64 Android,
  so the standard x86_64 emulator can no longer run these builds; test on a
  physical ARM64 device. A first build takes a long time; later ones reuse
  the IL2CPP cache. Running it saves those settings into `ProjectSettings`.
- **Release signing:** the build is a release build signed with the keystore in
  `~/.mood/` (`mood-release.jks`, with its passwords in `signing.properties`), or in the
  `MOOD_KEYSTORE`, `MOOD_KEYSTORE_PASS`, `MOOD_KEY_ALIAS` environment variables. The keystore is
  never in the repo. **Back it up**: an update only installs over an app signed with the same key,
  and a lost key means a new app. Without one the build falls back to a development, debug-signed
  APK and says so. The package id is pinned to `com.jceddy.moodswings`.
- **Run the Keystore tests on a device:** `ANDROID_SERIAL=<device> Unity.exe
  -batchmode -projectPath . -buildTarget Android -runTests -testPlatform
  Android -testFilter MoodSwings.Tests.AndroidKeystoreTests -testResults
  r.xml`. Unity builds a test player, installs it, and pulls results back.
- **Emulator gotchas** (from the 6.2-era x86_64 emulator runs; the same
  limits apply to any low-memory device): the default AVD has ~2 GB RAM, which a development
  build full of card art can exhaust (the test player then freezes and Unity
  reports "No activity received from the player in 600 seconds") -- move
  `Assets/Resources/CardArt` aside for device test runs. Also turn off
  Android's one-time full-screen prompt, which pauses the app until
  dismissed: `adb shell settings put secure immersive_mode_confirmations
  confirmed`.
- **Don't kill a headless device test run:** the test framework temporarily
  rewrites player settings (application id, splash screen, ...) and only
  restores them on a clean exit. If it's interrupted, `git checkout
  ProjectSettings/ProjectSettings.asset`.
- **Package id** is still Unity's default (`com.DefaultCompany.unityclient`);
  pick a real one before any release.

## Tools

Python scripts in `tools/` (`pip install pillow` for the first):

- `convert_card_art.py` -- converts `web-static/img` card art from WebP
  (which Unity can't import) to PNGs in `Assets/Resources/CardArt/`,
  named by catalog id. That folder is git-ignored; run the script after
  cloning. Our own replacement card faces live in `art-overrides/`
  (`<number>-<name>.webp`, e.g. `01-altruism.webp`); for those card numbers
  the script uses them instead of the web-static art, so replacing a card
  is just adding its file there and re-running. `--overrides DIR` adds
  another folder (PNG/WebP/JPG). `CardArtLibrary.ForCard(id)` loads from it. Art is sized to a
  multiple of 4 and imported without rescaling (`CardArtImporter`), which
  GPU texture compression requires -- otherwise Unity silently keeps each
  card as uncompressed RGBA32 (~3 MB instead of under 1 MB). Mipmaps are on
  (Kaiser filter, trilinear): cards are drawn at ~112 px from 744 px art, and
  without them the shrunken art is harsh, speckled noise.
- `make_tour_cards.py` -- writes the cards the welcome tour's sample game uses (art key, color, values, rules) to
  `Assets/Resources/Tour/sample-cards.json`, from the card catalog fixture.
- `fetch_emoji.py` -- downloads the emoji the chat can draw (see Chat and emoji above) into `Assets/Resources/Emoji/`.
- `publish_client.py` -- writes the update manifest for the builds (see Updates above) and, with `--upload`, publishes them.
- `capture_fixtures.py` -- logs in to a server with a throwaway account
  (credentials from `MOODSWINGS_USER`/`MOODSWINGS_PASSWORD`) and saves
  read-only API responses, email/phone redacted, to
  `Assets/Tests/Fixtures/` for model tests.

## Welcome tour

The first time someone reaches the main menu on a device, a tour walks them through the app: a welcome, then a step for each
of the menu's buttons (Play, Puzzles, Decklists, Friends, Achievements, Tournaments, Stats, Settings) with the screen dimmed
and a frame round the button being described. Two steps then take the player into Settings, scroll to the two switches that
change which games they can start and who with -- **Show custom card/effect formats** (what offers Chaos Draft and the other
custom formats) and **Discoverable for open games** (whether strangers can see and join what they post to the open lobby) --
and frame them, then bring them back to the main menu for a picture of the table and what is where on it, and a last word on
how to see the tour again. Each step has **Back** and **Next** (**Done** at the end), and **Skip the tour** is there at every step; Back
or Escape (Android's Back button too) skips as well. Finishing and skipping both count as having seen it
(`DeviceSettings.TourSeen`, per device), so it doesn't start by itself again.

After the picture of the table the tour offers **a sample game**: a short game between two bots, MarkBot (you, along
the bottom) and AriBot, played out one move at a time (23 of them, five rounds of a Traditional game with the Structure deck).
Each move draws the table at the left -- both seats with their scoreboards (the score, a trophy for each round won, the
cards in hand), the moods in play with their real art, and the shared discard pile -- with a frame round each thing the
commentary is about, and the commentary at the right, with the rules it brings up ("Rule: The highest score wins the
round."). The cards are drawn the way the board draws them, so a mood on its alternate value is upside down and a
suppressed one lies on its side. The step before it has **Skip the sample game**, which goes on to what changes with more
players; Back, Skip the tour and Escape work in the game as anywhere in the tour. The game is data, not a recording:
`SampleGame` (Core) says what happens in each move and works every table out from the cards, so its scores are checked
against the numbers in the commentary by a test; `SampleTable` (UI) draws it; the cards come from
`Assets/Resources/Tour/sample-cards.json` (made by `tools/make_tour_cards.py` from the catalog fixture).

**Settings > Welcome tour > Show the welcome tour** takes the player back to the main menu and runs it again. If an update is
waiting, its box comes up after the tour, not on top of it. Signing out or being sent to another screen mid-tour ends it.

What it says is `TourSteps` (`Assets/Scripts/Core/WelcomeTour.cs`): change the text, or add a step by giving it a `Target`
(a main menu button -- `HomeScreen.TourTarget` knows them by name) or none. `TourFlow` is the state (UI-free) and
`TourOverlay` draws it; a step's `Screen` says which screen it is on (the tour moves the player there and back, and a test pins
the two switches' names to `PreferenceCatalog`'s labels). PlayMode tests start with the tour off (`MainSceneTests.ShowTour`), or it would cover every test's
main menu.

## Updates

The Windows, macOS and Android apps look for a newer version once each time they start (when the player gets to the
main menu), and from **Settings > Check for updates now**. **Settings > Check for updates** switches the start-up
look off. The look is one small download of a manifest at a fixed address, `UpdateConfig.ManifestUrl`
(`Assets/Scripts/Core/UpdateFlow.cs`), by default `https://github.com/jceddy/MoodSwings-Web/releases/download/client-latest/latest.json`.
A check that can't be made (offline, no manifest yet) says nothing. The Editor never checks.

```json
{ "version": "1.3.0", "released": "2026-10-20", "notes": ["What is new, a line each"],
  "windows": { "url": "...MOOD-Setup-1.3.0.exe", "sha256": "..." },
  "macos":   { "url": "...MOOD-1.3.0-mac.zip",   "sha256": "..." },
  "android": { "url": "...MOOD-1.3.0.apk",       "sha256": "..." } }
```

When `version` is newer than the app's (`bundleVersion`, compared number by number) and the platform has an entry, a box
offers **Update**, **Later** (asks again next start) and **Skip this version** (quiet until a newer one is published;
a manual check still shows it).

- **Windows** downloads the installer to a temp folder with progress, checks its SHA-256 against the manifest, starts it
  and quits so the installer can replace the app. A failed download says why and can be retried.
- **macOS** and **Android** open the download in the browser (the macOS zip is unpacked by hand; the Android apk is
  installed from the notification -- the phone asks once to allow installs from the browser). Android needs no Play
  Store for this; the Play Store is only needed for updates the system applies for you.

Publishing: build the clients, then `python tools/publish_client.py --note "What is new"` writes `Build/latest.json`
(hashing each build; a platform with no build is left out). Adding `--upload` puts the builds and the manifest on the
`client-latest` GitHub release with `gh` (the manifest last). Nothing is uploaded without that flag. Note the
repository is public, so builds on its releases are downloadable by anyone; point `ManifestUrl` and the script at
another host to change that.

## iOS

The project can make an Xcode project for an iPhone or iPad build -- **MoodSwings > Build iOS Xcode Project** in the
Editor (`IosBuild`; headless:
`Unity -batchmode -quit -buildTarget iOS -executeMethod MoodSwings.Editor.IosBuild.Build`), which needs the Editor's
"iOS Build Support" module and writes `Build/iOS/Unity-iPhone.xcodeproj` -- and Xcode, on a Mac, turns that into the app.
**[docs/building-for-ios.md](docs/building-for-ios.md)** is the step-by-step guide to building it on a Mac and installing
it on a device over USB, with no paid Apple account needed.

- **Settings it applies:** bundle id `com.jceddy.moodswings` (`MOOD_IOS_BUNDLE_ID` overrides it), iPhone and iPad,
  landscape, iOS 15 or later, full screen only (no iPad split view), IL2CPP / ARM64, automatic signing
  (`MOOD_IOS_TEAM_ID` sets the team; `MOOD_IOS_BUILD_NUMBER` the build number), and the app icon from `Assets/Icons`.
  `IosPostProcess` marks the app as exempt from export-compliance questions (`ITSAppUsesNonExemptEncryption`).
- **What's missing on iOS:** in-app updates (and so the update settings), push notifications (APNs), the art-pack file
  picker, vibration and Quit; everything else is the shared client.
- **Not yet verified:** the machine the client is built on is Windows, which can't build for iOS, so the iOS build,
  the Keychain plugin and the layout on a real iPhone/iPad are untested. The Editor scripts compile; nothing has run.

## Mobile + desktop from one project

Nothing here is platform-specific yet -- that's mostly a Build Settings
and input-handling concern once there's an actual scene/UI to build:
Unity's Input System can define separate control schemes (touch vs.
mouse/keyboard/controller) against the same game logic, and a
`CanvasScaler` set to "Scale With Screen Size" handles the aspect-ratio
spread across phones/tablets/desktop monitors. The one hard platform
constraint: an iOS build has to go through Xcode on an actual Mac --
that step can't be done from Windows/Linux at all (see "iOS" below).

## Versioning

This client is **not** part of `VERSION` at the repo root -- that file
tracks `php-app`/`database`/`web-static` deploying together as one
site (see the root `README.md`'s "Versioning" section). This client
consumes that backend as an API client and can version/release on its
own schedule; it doesn't need a schema-version-bump migration the way a
backend change does.
